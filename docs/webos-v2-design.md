# 访问端浏览器 WebOS v2 设计方案（重写版）

> 替代旧「访问端电脑浏览器 WebOS」章节。回答一个问题：**做成真远程桌面（打通 RDP），还是在浏览器里重做一个操作系统（每个模块分别映射）？**
> 结论先行：**重做为 WebOS（模块映射 + 通用窗口接管），不打通 RDP 协议。** 详见 §1。

---

## 0. 现状盘点（代码实态）

插件侧（本仓库）已经具备的能力，全部经 `/__ph/*` 端点暴露、访问端浏览器可直达：

| 能力 | 端点 | 现状 |

| 点击注入（窗口坐标归一化） | `/__ph/click` | ✅ 有 |

| 启动程序 | `/__ph/apps/open`（.lnk，限枚举目录）、`/exec/launch`（8 个 exe 白名单） | ✅ 有，**白名单过紧** |

**缺口**（v2 要补的）：启动后没有"接管窗口"的闭环；实况只有轮询帧没有连续视频；没有任务栏/窗口切换语义；文件管理是工具面板不是资源管理器；启动白名单和真实开始菜单不一致（用户点开始菜单里的程序被拒）。

## 1. 路线评估：远程桌面 vs 重做系统

### 1.1 方案 A：真远程桌面（打通 RDP 协议）

把访问端浏览器变成 RDP 客户端（Apache Guacamole 模式：浏览器 ↔ guacd ↔ RDP 3389），授权用现有 E2E 配对体系在前置网关完成。

**五个硬问题，按致命程度排序：**

1. **Windows 家庭版没有 RDP 服务端。** 家用电脑大量是 Home 版，3389 根本不接受连接。要么劝用户升 Pro，要么换第三方服务端——路线天然抛弃一部分用户。
2. **控制台语义冲突。** RDP 登录会锁定/接管物理控制台（或另开会话），坐在电脑前的用户看到锁屏。本产品的核心场景是"**自己**的电脑、随时随地用"，RDP 的会话语义和手机→自己电脑的场景直接打架。
3. **授权体系两套化。** RDP 的 NLA 需要 Windows 本地账户凭据。要么把 E2E 配对授权翻译成 RDP 凭据注入（等于自建 RDP 网关，工程量不比 WebOS 小），要么并存两套登录——安全审计（台账）还得自己补，RDP 内部操作对数据总线全黑盒。
4. **带宽与中继成本。** 1080p 桌面视频 2–10 Mbps，现有云端中继扛全量用户屏推会显著抬成本；手机弱网下降级链路复杂。
5. **攻击面。** 暴露 RDP 协议栈（哪怕在网关后）是历史漏洞重灾区，与本项目"云端只见 E2E 密文"的最小信任设计相悖。

### 1.2 方案 B：浏览器 WebOS（模块映射）

浏览器里重做一个桌面壳，把电脑能力**逐模块映射**成 Web 组件：开始菜单→应用启动器，资源管理器→文件模块，任务栏→窗口模块，"用程序"→窗口实况+输入注入。

**优势：**
- 任意 Windows 版本可用；不锁控制台，电脑前的人无感知；
- 带宽按需：平时只传 JSON，看视频才传画面（比 RDP 常开视频流省一个量级）；
- 每个模块天然落在现有安全体系里：数据总线四级分级、台账逐条留痕、启动审计——RDP 给不了这些；
- 手机端交互友好（原生为触摸设计，不是把桌面鼠标搬上小屏）。

**短板：**
- 未映射的桌面软件没有"通用入口"——旧版只能操作白名单程序，这是"不像远程桌面"的病根；
- 复杂软件（设计工具、游戏）靠点击镜像操作体验有限。

### 1.3 关键洞察：要的是"远程桌面的**效果**"，不是"RDP **协议**"

Chrome Remote Desktop、向日葵、ToDesk、RustDesk——**没有任何一家用 RDP 协议**。它们全部是：**屏幕采集（DXGI Desktop Duplication / GDI 抓屏）→ H.264 视频流 + 输入注入（SendInput）**。这条路：
- 不受家庭版限制（是用户态抓屏，不是远程会话）；
- 不锁控制台；
- 不需要 Windows 凭据，授权完全走自己的 E2E 体系；
- 带宽可控（差异帧编码 + 静止画面几乎零流量）。

### 1.4 结论：**WebOS 为主干 + 通用窗口接管层**，三层递进

```
第 1 层：模块映射（开始菜单/资源管理器/任务栏/数据总线）——主力，日常 90% 操作
第 2 层：通用窗口接管（任意程序：启动 → 窗口实况 → 点击/键盘注入）——补齐"用程序"
第 3 层：全屏桌面实况（连续视频流 + 注入，Chrome Remote Desktop 模式）——兜底任意角落
```

RDP 仅作为第 3 层的**可选后端**（Pro 版用户可切换，用 Guacamole 思路内嵌），不作为主线。三条线共用同一套 E2E 授权和台账。

## 2. 目标体验定义

访问端浏览器打开 `/os` 即进入一个桌面：

- **桌面壳**：壁纸 + Dock/任务栏 + 开始菜单按钮，多电脑可切换/并排（复用 targets registry）。
- **开始菜单**：枚举目标电脑真实开始菜单（现有 `/apps/list`），点击即启动（放开白名单，改审计制）。
- **资源管理器**：窗口化文件管理（现有 files 端点升级为 Web 文件管理器：目录树、上传下载、预览、右键菜单、拖到 Dock 快速发送）。
- **任务栏**：目标电脑真实窗口列表 → 点选即"接管"该窗口；支持最小化/关闭/切换。
- **用程序**：启动后自动弹出该窗口的实况画面，可点可输；非映射软件走全屏实况兜底。
- 全程操作记台账（app-launch / remote-key / click / 文件读写均有留痕）。

## 3. v2 架构

```
访问端浏览器（/os WebOS 前端，桌面壳 + 窗口管理器）
   │  ① JSON API（同端 Cookie / v1 Cookie）
   │  ② 视频流 WS（H.264，P2P 优先，中继兜底）
   ▼
云端中继 ──E2E（Ed25519 + X25519 + AES-256-GCM）──► 目标电脑 person-harness-plugin
                                                         ├─ onToolRequest：/__ph/*（现有 + 增量）
                                                         ├─ 视频采集器（新增：DXGI/GDI → H.264）
                                                         └─ 输入注入（现有 click/key + SendInput 扩展）
```

**增量组件（都在插件进程内，不引入外部服务）：**

| 组件 | 职责 | 状态 |
| --- | --- | --- |
| `video-source.mjs` | 屏幕/窗口采集：优先 DXGI Desktop Duplication（Win8+，差分帧、GPU 加速），回退 GDI BitBlt 区域抓帧 | 新增 |
| 编码 | `ffmpeg`（随插件打包或依赖系统）→ H.264 baseline，静止降码、运动升码 | 新增 |
| `stream-server` | 复用现有 V5 P2P 打洞：视频走直连 socket，失败回落中继 WS | 新增（复用 punch/隧道） |
| `window-agent` | 窗口生命周期跟踪（启动的 pid → hwnd → 实况绑定）、任务栏事件（uiautomation/EnumWindows 轮询） | 新增 |

## 4. 模块设计（重写各模块）

### 4.1 开始菜单 / 启动器
- 数据源不变（`/apps/list` 枚举四个 .lnk 根目录 + 图标懒加载缓存）。
- **去掉启动白名单**：`/apps/open` 已限定"lnk 必须在枚举根目录内"，路径注入面已封死，白名单纯属体验负资产，改为全量可启 + 台账 `app-launch`。
- 前端按 grp（start/desktop）分组，支持搜索过滤；最近启动按台账排序置前。

### 4.2 资源管理器（Web 文件管理器）
- 端点沿用 `files/list|get|put|preview`；前端做成桌面壳里的多标签窗口（不是现在的悬浮面板）：
  - 目录树 + 面包屑 + 缩略图预览（图片走 `file/preview`）；
  - 上传/下载（分片上传突破 25MB 限制，端点加 `file/put-chunk`）；
  - 右键菜单：下载/预览/重命名/删除（**删除默认不出现**，与数据总线分级联动：敏感/禁碰目录只读）。
- 跨电脑文件互传沿用 databus-ui 的思路，升级为 WebOS 内拖拽：A 电脑资源管理器 → 拖到 B 电脑窗口。

### 4.3 窗口管理 / 任务栏
- 新端点 `/__ph/windows/watch`：服务端维护窗口快照（标题/hwnd/图标/前台状态），变化推送（WS mux 已有透传通道），替代前端轮询。
- 任务栏 = 前台窗口高亮 + 点击切换（复用现有 ShowWindow/SetForeground PS）。
- 最小化/关闭：`/windows/ctl {hwnd, op: minimize|close|restore}`。

### 4.4 用程序（启动 → 接管闭环）⭐ 核心增量
链路：`/apps/open {lnk}` → 返回 `pid` → `window-agent` 按 pid 找到主 hwnd（≤5s 轮询）→ 前端自动打开该 hwnd 的接管窗口：
- **窗口实况**：`live/frame` 轮询升级为按需视频通道（见 §4.5），窗口失焦/最小化自动暂停编码。
- **输入注入**：点击（已有，坐标归一化回窗口客户区）+ 键盘（已有 `remote-key`）+ 增量补充：
  - `/key/raw {vk, down|up}`：修饰键、方向键、快捷键（Ctrl+C/V/S）——现在逐字输入覆盖不了快捷键；
  - `/input/scroll {dx,dy}`：滚轮注入；
  - 剪贴板通道联动：手机上复制 → 电脑剪贴板 → 快捷键粘贴（现有 clipSetSync 已有雏形）。
- 接管窗口 Chrome：标题栏显示被控程序名 + 「这台电脑的物理使用者能看到你的操作」提示条。

### 4.5 全屏桌面实况（第 3 层兜底）
- `video-source.mjs` 全屏采集 → H.264 → 直连优先 WS 推流；前端 `<video>` 播放 + 全屏坐标映射注入。
- 触发场景：接管窗口按钮「全屏操作」、WebOS 桌面空白处双击、未识别程序兜底。
- 码率自适应：静止桌面 100–300kbps，拖动窗口 1–2Mbps；弱网先降分辨率后降帧率。

### 4.6 多电脑联邦
- 沿用 targets registry；WebOS 前端把每台电脑变成一个"桌面空间"（切换/并排）。
- 联邦检索保留现有 60s TTL 缓存早停方案（防"联邦检索卡死"旧病复发）。

## 6. 授权模型

- 沿用现状：设备配对（Ed25519）→ 访问端拿到 v1 owner Cookie → `__ph/*` 同源可达。
- **新增视频通道授权**：开实况/接管前检查 `stream` 权限位（台账记 `stream-start`，含时长与目标窗口）。
- 电脑前的物理使用者拥有最高权：WebOS 接管窗口活动时本机弹出可关的提示气泡（默认开，可在 `/ph` 配置关闭）。
- 沿用 E2E 纪律：视频流经中继时云端只见密文；P2P 直连不落地服务器。

## 7. 安全边界（继承并收紧）

1. 启动只认"枚举根目录内的 .lnk"——继续拒绝任意路径/任意 exe（`apps/open` 校验保留）。
2. 输入注入（点击/键盘/滚轮）每次调用留痕；键盘注入限速（防恶意批量输入）。
3. 视频流只在会话内存在，不落盘；截图/实况帧返回后由前端持有，服务端不缓存帧。
4. 文件写操作（上传/删除）在敏感/禁碰目录一律拒绝，与数据总线分级共用同一份判定。
5. 删除类操作永不自动执行（继承磁盘清理模块的铁律）。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| DXGI 采集在某些老显卡/远程会话内失败 | GDI BitBlt 回退；采集失败自动降级到现有轮询帧 |
| 家庭版/单显示器环境差异 | 采集与窗口坐标逻辑按虚拟屏矩形处理，不假设单屏 |
| 高码率冲爆中继 | 直连优先（V5 P2P 已就位）；中继模式限 1Mbps 硬顶 + 降分辨率 |
| 输入注入被游戏/管理员程序吞掉（UIPI） | 注入进程以中等完整性运行可覆盖常规软件；管理员程序标注"不可接管"灰显 |
| 前端复杂度膨胀 | 桌面壳保持单页零构建（与 bridge-toolbar 同款策略），模块懒加载 |

## 10. 本机 shim 带宽实测（2026-10-26 历史数据）

> **口径提醒**：本节保留采集引擎优化前后的历史对照，不再作为线上容量或套餐分档依据。2026-10-28 完整公网中继与 E2E 复测见 §11；文件线上载荷约为原始内容 2.37–2.39 倍，动态实况约 145 KB/s。

**测量方法**：本机（1920×1080）经 shim `/api/ph-webos/api` 模拟前端真实轮询参数实测；统计响应体字节（JSON 含 base64 载荷，未计 HTTP/TCP 头）。当时假设“云端中继 WebSocket 包装增量约 2–5%”，该假设已被 §11 完整链路复测否定，不能用于推算当前线上字节。窗口实况动态场景用持续刷屏的控制台窗口（每帧画面必变，即最坏情况）。

| 场景 | 参数 | 单帧 | 平均带宽 | 折算小时流量 |
| --- | --- | --- | --- | --- |

**实测顺带发现的工程事实**：
1. **采集延迟就是帧率天花板**：PS 冷启动管线 p50 ≈ 918ms（引擎上限 ≈1fps）。**P3 已落地（2026-10-26）**：`lib/capture-helper.cs`（csc 编译的常驻采集进程，`CaptureDaemon` 管理：懒拉起/串行队列/15s 超时/空闲 15min 回收，PS 管线永久兜底）——窗口帧 **p50 26ms**（35×），微缩图容差变化检测移入进程内，实测开始菜单开合即时触发、静止零流量。前端接管窗口改自适应轮询（变化时 350ms ≈3fps，静止退避 1200ms）。远期 ≥5fps 连续视频（H.264 推流）仍是 Pro 档工程。已知限制：控制台（conhost）窗口 PrintWindow 可能给陈旧画面（Windows 自身限制，旧管线同样存在），GUI 窗口无此问题。
2. **全屏实况 JPEG 化已完成（2026-10-26）**：`/__ph/screenshot` 新增 `fmt:'jpeg'` 模式（虚拟整屏采集→1280 缩放→q60），变化检测不用整帧哈希——任务栏时钟秒数/光标闪烁会让每帧 JPEG 字节都不同，改为 **64×24 微缩图逐像素容差比对**（通道差>10 记 1 像素，≤8 像素判静止）。实测静止桌面首帧后全部 changed:false；旧 PNG 模式 337 KB/s → 新模式静止≈0。代价：鼠标在纯色背景上移动（<8 微缩像素）不触发刷新——只读实况可接受，交互走窗口接管。
3. **窗口实况的静止零流量机制有效**：changed:false 让"挂着不操作"几乎不耗流量，计费上适合"按活跃时长"而非"按连接时长"。

**计费分档建议（以中继流量成本为核心）**：

| 档 | 内容 | 流量特征 | 成本量级 |
| --- | --- | --- | --- |
| 免费/基础 | 文字对话 + 文件管理 + 窗口总览 | <1 KB/s，静止≈0 | 可忽略 |
| 标准 | 窗口实况接管（现能力） | 0–50 KB/s，活跃才计费 | ~180 MB/h 活跃 |
| 高配 | 全屏远程桌面（JPEG+容差变化检测，2026-10-26 已落地） | 静止≈0，动态 0–40 KB/s | ~140 MB/h 活跃 |
| Pro（远期） | P3/P4 连续视频（H.264、≥5fps） | 0.1–2 Mbps 自适应 | 按 P5 RDP/Guacamole 或直连优先摊薄 |

注意：以上为受控电脑上行需求；经云端中继时流量在「访问端↔云端」「云端↔受控电脑」各计一次。全屏实况 JPEG 化后单帧 47KB，云端桥接 30s 超时在 0.5 Mbps 以上上行的受控电脑即可稳定通过。

### 11.3 容量与分档校准

- 持续动态实况统一按约 **145 KB/s** 规划，约 **0.52 GB/h**（十进制，手机侧双向中继载荷）。
- 200 Mbps 公网峰值预留 30% 后为 140 Mbps，动态实况规划并发约 **117 路**，替代旧 341 路估算。
- 免费 64 KB/s 无法持续跑满本轮动态实况；标准 512 KB/s 可覆盖一路并留余量。套餐限速值不等于功能实测消耗。
- 文件线上放大约 **2.37–2.39 倍**；64 KB/s 线上档位对应的有效文件内容速率约 **27 KB/s**。
- 这些是当前受控桌面、1280 宽 JPEG 参数与测试窗口的结果，不代表所有视频、复杂网页、多屏或不同清晰度场景；持续用真实 usage 数据校准。
